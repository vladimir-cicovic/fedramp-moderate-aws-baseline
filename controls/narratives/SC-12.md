# SC-12 Cryptographic Key Establishment and Management

| Family | Baseline | Responsibility | Status |
|---|---|---|---|
| System and Communications Protection | Moderate | Shared (AWS KMS generates and stores keys in HSMs; customer owns policies and lifecycle) | Implemented |

Enhancements addressed: SC-12(1) availability (KMS multi-AZ, key material
never exported, deletion window).

## Control summary

Establish and manage cryptographic keys when cryptography is employed within
the system in accordance with key management requirements: generation,
distribution, storage, access, destruction.

## FedRAMP Rev 5 parameters

- Keys generated and protected by FIPS 140 validated modules; NIST SP 800-57 lifecycle practices; rotation per organizational policy (annual for symmetric data keys here).

## Implementation

**Generation and storage.** All keys are AWS KMS customer managed symmetric
keys (AES-256) generated inside FIPS 140-3 Level 3 validated HSMs. Key
material never leaves KMS; services receive data keys through envelope
encryption. Three keys exist, one per purpose, so a compromise or policy
error affects one domain:

| Key | Alias | Used by |
|---|---|---|
| logging | `alias/fedramp-baseline-lab-logging` | CloudTrail buckets, every CloudWatch Logs group, Config delivery, Lambda environment, SQS DLQ |
| alerts | `alias/fedramp-baseline-lab-alerts` | SNS alerts topic |
| data | `alias/fedramp-baseline-lab-data` | EBS default encryption, Aurora storage and Performance Insights, Secrets Manager database secret |

**Access (key policies).** Each policy has a root statement (so the key can
never become unmanageable), then service-principal statements with
conditions: CloudTrail only with the encryption context and `aws:SourceArn`
of the named trails, CloudWatch Logs only for log groups in this account and
region, Config and the alert publishers only with `aws:SourceAccount`. The
data key policy separates administrators (manage, cannot encrypt) from users
(encrypt, cannot manage) and allows grants only for AWS resources
(`kms:GrantIsForAWSResource`). The management account gets `kms:DescribeKey`
on the logging key only, for the organization trail.

**Rotation.** Automatic annual rotation is enabled on all three keys
(`rotation_period_in_days = 365`); old material remains for decryption, new
material encrypts going forward. Database and application secrets rotate
independently (RDS-managed).

**Destruction.** `ScheduleKeyDeletion` has a 7-day waiting window in the lab
and 30 in production; the protect-security-services SCP denies
`kms:ScheduleKeyDeletion` and `kms:DisableKey` to everyone but SecurityAdmin,
and a CloudWatch alarm fires on either action.

**Audit.** Every key use is a CloudTrail event with the encryption context;
Security Hub KMS.1 to KMS.4 check for exposed or unrotated keys.

## Evidence

| Artifact | Collection |
|---|---|
| Key metadata and rotation | `aws kms describe-key`, `get-key-rotation-status` for each alias |
| Key policies | `aws kms get-key-policy --policy-name default` |
| Alarm `kms-key-disabled-or-scheduled-deletion` | `aws cloudwatch describe-alarms` |
| Security Hub KMS.1 to KMS.4, CloudWatch.7 | Security Hub export |
| Which resources use which key | `docs/resource-inventory.md` |

## Gaps and POA&M

- Administrator and user ARN lists for the data key are empty in the single-operator lab; populate with the SecurityAdmin and workload roles in production.
- Multi-region keys for a DR region are a production design item (CP-9).
